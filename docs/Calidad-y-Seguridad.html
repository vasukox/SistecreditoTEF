Security

Seguridad del software

La seguridad se modela en cuatro capas concéntricas de defensa: si una capa falla, las demás siguen protegiendo. Este modelo viene del manual de HioPosCloud §6.1 y se implementa capa por capa con medidas concretas en código.

Figura 2 — Defensa en profundidad: 4 capas concéntricas. Cada capa asume que las demás pueden fallar.

Datos sensibles: política de tratamiento

Aplicamos la matriz del manual §6.2 con tres políticas claras: prohibido, enmascarado y aceptable.

DatoRiesgoPolíticaImplementación
Subscription-Key ALTA Nunca en logs HttpLoggingHandler.IsSensitiveHeader() → ***REDACTED***
Cédula (idDocument) MEDIA Enmascarada en URL Regex enmascara → **********1234
OTP / Token ALTA Nunca persistido Solo en OtpViewModel.CodigoOtp (memoria)
creditId MEDIA OK en logs internos Reconciliación + auditoría Permoda
Mobile / Email MEDIA Solo memoria En Client in-memory; state.Clear() tras TX

Medidas implementadas

Cada medida está respaldada por una clase específica del proyecto que la implementa.

Certificate Pinning

CertificatePinning.cs valida el SPKI SHA-256 del certificado contra cfg.CertificatePins. Vacío = TLS estándar; con pins = seguro.

SQLCipher

SQLitePCLRaw.bundle_e_sqlcipher activo. La BD idempotency.db3 queda cifrada AES-256 en reposo.

Redacción Subscription-Key

IsSensitiveHeader() oculta Ocp-Apim-Subscription-Key y Authorization en headers, body y logs.

Enmascarar cédula

Regex (idDocument=)(\d+) enmascara los primeros dígitos dejando solo los últimos 4.

Reintentos con Polly

CredinetHttpPolicies.cs reintenta solo fallos transitorios y solo en GETs idempotentes. Excluye OTP y POST.

state.Clear() tras TX

Antes de FinishWithResult se limpia cliente, crédito, documento y monto de la memoria.

Design principles

Principios de diseño

El proyecto se adhiere a tres familias de principios: SOLID (diseño orientado a objetos), DRY (una sola fuente de verdad) y KISS (simplicidad sobre generalización prematura).

Figura 3 — Los 5 principios SOLID. Cada color representa un pilar de diseño distinto.
S · Single

Single Responsibility

Cada clase tiene una sola razón para cambiar. SistecreditoService orquesta lógica de dominio; no sabe nada de HTTP, SQLite ni Android Intents.

public class SistecreditoService {
    // Solo orquesta, no sabe de Android
    private readonly ICredinetRepository _repo;
    private readonly IAuditLogger _audit;
    private readonly IIdempotencyStore _idempotency;
}
O · Open

Open / Closed

Extensiones sin modificar. Los enums DocumentType y CreditFrequency exponen mapeos como métodos de extensión.

public enum DocumentType { CedulaCiudadania, CedulaExtranjeria }

public static class DocumentTypeExtensions {
    public static string Code(this DocumentType t) => t switch {
        DocumentType.CedulaCiudadania  => "CC",
        DocumentType.CedulaExtranjeria => "CE",
    };
}
L · Liskov

Liskov Substitution

Las implementaciones son intercambiables. ITransactionResultHandler tiene una implementación real y una NoOp para tests.

public interface ITransactionResultHandler {
    void FinishWithResult(HioposResponse response);
}

// Producción
public class AndroidTransactionResultHandler : ITransactionResultHandler { ... }

// Tests
internal class NoOpTransactionResultHandler : ITransactionResultHandler { }
I · Interface

Interface Segregation

Interfaces pequeñas y específicas. Separamos ITransactionResultHandler, ITransactionStateStore e INavigationService.

// El VM pide solo lo que necesita
public partial class ConfirmacionViewModel(
    ITransactionStateStore state,
    ITransactionResultHandler resultHandler,
    ReceiptBuilder receiptBuilder,
    INavigationService nav) : ObservableObject;
D · Dependency Inversion

Dependency Inversion

Las dependencias apuntan a abstracciones, no a concreciones. Toda la inyección se configura en MauiProgram.CreateMauiApp.

// MauiProgram.cs — un solo lugar, todas las dependencias
builder.Services.AddSingleton<ICredinetRepository, CredinetRepository>();
builder.Services.AddSingleton<IAuditLogger, BroadcastAuditLogger>();
builder.Services.AddSingleton<ITransactionResultHandler, AndroidTransactionResultHandler>();
// Tests inyectan fakes sin recompilar la app.
DRY

Don't Repeat Yourself

Cada constante vive en un único lugar. Cambiar el nombre del APK se hace en una sola línea:

// HioposActions.cs
public const string ApkName = "sistecredito";
private const string Prefix = "icg.actions.electronicpayment." + ApkName + ".";

public const string Initialize  = Prefix + "INITIALIZE";
public const string Transaction = Prefix + "TRANSACTION";
// ... las 11 actions se generan desde aquí

Otras "single sources of truth": ApiConfig (URL/headers), HioposCapabilities (18 flags), CredinetMapper, ReceiptBuilder.

KISS

Keep It Simple, Stupid

Preferimos la solución obvia. Tipos de retorno seguros en vez de excepciones para control de flujo.

// En vez de lanzar y atrapar excepciones...
public abstract record ApiResult<T> {
    public sealed record Ok<U>(U Data)   : ApiResult<U>;
    public sealed record Failure<U>(ApiError Cause) : ApiResult<U>;
}

// El VM hace pattern matching, sin try/catch de control:
switch (result) {
    case ApiResult<Client>.Ok<Client> ok: /* happy */
    case ApiResult<Client>.Failure<Client> f: /* error */
}

Architecture

Arquitectura: el porqué

La elección de separar View ↔ ViewModel ↔ UseCase ↔ Service ↔ Repository no fue caprichosa: cada límite existe para resolver un problema concreto.

Figura 4 — Las 5 capas de la aplicación. Cada capa depende solo de la capa inferior.
Testabilidad. El SistecreditoService se testea con FakeRepo que no toca red. Tests corren offline en milisegundos.
Mantenibilidad. Cambiar la UI no toca la lógica de dominio. Cambiar la API no toca la UI.
Sustituibilidad. Reemplazar HttpLoggingHandler por Serilog no rompe nada — solo se cambia el binding.
Demo vs Producción. SistecreditoService detecta IsSyntheticDemo y devuelve datos sintéticos sin red. La UI es la misma.

Records, inmutabilidad y DTOs

Usamos record para todos los modelos de dominio y DTOs. Por qué: inmutabilidad, igualdad por valor, serialización trivial, sintaxis concisa.

public record Credit(
    string TypeDocument,
    string IdDocument,
    string CreditId,
    int    CreditNumber,
    double EffectiveAnnualRate,
    // ...
);

Async/await y cancelación

Reglas: todo I/O es async, sufijo Async obligatorio, sin .Result/.Wait(), sin ConfigureAwait(false) en UI.

// VM: continuacion en UI thread para bindings + Shell
public async Task ValidarAsync() {
    var result = await service.ValidarClienteAsync(
        TipoDocumento, NumeroDocumento);
    switch (result) {
        case ApiResult<Client>.Ok<Client> ok:
            // bindings actualizados, Shell.GoToAsync
    }
}

Nullable reference types

<Nullable>enable</Nullable> activo. DTOs nullable (string?, double?); dominio no-null con defaults aplicados en mapper.

// DTO: nullable porque el backend puede omitir
public record ClientDto(
    [JsonPropertyName("creditLimit")] double? CreditLimit,
    [JsonPropertyName("email")] string? Email);

// Dominio: no-null (mapper aplica defaults)
public record Client(
    DocumentType DocumentType,
    string DocumentId,    // nunca null
    double CreditLimit);   // nunca null

Inyección de dependencias

Toda dependencia se inyecta por constructor. Nunca Service Locator. El contenedor se configura en MauiProgram.

⚡ Capacidad punta por tienda

1 POS × 20 TX/min × 60 min = ~1.200 TX/hora por terminal. Para 5 POS simultáneos (caso real de tienda grande): 6.000 TX/hora. Más que suficiente para día pico de Black Friday.

🔋 Impacto en batería

Cada TX consume ~0.3% de batería en terminal estándar (medición conservadora). ~300 TX por carga completa con la pantalla activa. Por encima de 8h de operación continua sin recarga.

🔄 Reintentos con Polly

2 intentos con backoff 250ms / 500ms. Solo en GETs idempotentes: validar, simular, activos, mes límite. Excluye getCreditToken (no duplica SMS) y todo POST (no duplica crédito).

⏰ Techo de espera máximo

Si todo va mal: ~31 segundos (30s timeout global + 0.75s de reintentos). Después de eso, ApiError.Network con mensaje claro para el cajero. Sin cuelgues infinitos.

🧪 Si quieres probarlo a fondo

Plan de pruebas sugerido, en orden de esfuerzo. Empieza por el ① que toma 5 minutos; el ⑥ es para certificación previa a go-live:

① · 5 min SANDBOX

Smoke test

1 transacción manual con cliente 1026260942. Tiempo esperado: ~8-10s (incluye tipeo). Verifica el path feliz.

② · 8h CARGA

Día completo

50 TX/hora × 8h = 400 TX en una tienda simulada. Métricas: p95 latency < 2s, error rate < 1%. k6 o NBomber.

③ · 15 min CONCURRENCIA

Pico concurrente

5 transacciones simultáneas en 5 POS distintos (mismo SaleId). Validar que SqliteIdempotencyStore no corrompe bajo escritura concurrente.

④ · 30 min CHAOS

Resiliencia

Tirar WiFi durante el flujo. Verificar error claro al cajero y que state.Clear() limpia memoria. Sin crashes, sin loops infinitos.

⑤ · 10 min IDEMPOTENCIA

Re-disparo de TX

Disparar 3 veces el mismo SaleId. Las 3 deben devolver el mismo CreditId (cache hit, sin doble cobro).

⑥ · 2h HARDENING

SQLCipher 100 TX

100 TX rápidas seguidas. Validar que la BD cifrada no se corrompe bajo carga (SQLite WAL + AES-256).

Wrap-up

Conclusiones

SistecreditoTEF es un módulo pequeño en líneas de código (~3.500 LoC + tests) pero denso en responsabilidades contractuales: 11 acciones HioPos, 7 endpoints CREDINET, eco de 14 extras, persistencia cifrada, auditoría broadcast.

Las decisiones de diseño — capas MVVM + service, contratos tipados con ApiResult<T>, inyección estricta, configuración externalizada, security-by-default — no son accidentes: son la respuesta directa a los problemas que el manual de HioPos y Credinet describen.

Lo que ya está resuelto

  • Funcionalidad end-to-end completa
  • 7 endpoints CREDINET
  • 11 intent-filters HioPos
  • SQLCipher activo en BD local
  • Cert Pinning + Polly + Redacción
  • Idempotencia por SaleId
  • Eco de 14/14 extras a HioPos
  • Demo mode + Producción por config

Pendientes para go-live

  • Pruebas de carga formales (k6/NBomber)
  • Migrar Preferences → SecureStorage (opcional)
  • Tablas audit_log + error_log en SQLite
  • Serilog opcional (logs estructurados)
  • Hash de cédula en logs (no solo URL)
  • Pin SPKI real de api.credinet.co
  • Coordinación con ICG (CloudLicense)
  • Coordinación con Sistecredito (key prod + IP whitelist)
